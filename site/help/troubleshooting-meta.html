Meta shows no conversions

Why Meta shows no conversions, and how to check the outbound send to the ad platform without leaving the tracker.

Updated 5 October 2026

Work the checks in order

“Meta shows no conversions” almost always means the tracker recorded the conversion, but the outbound send to Meta never ran or was refused. Work the checks in order — each rules out a class of cause before the next. Every send attempt is visible in Logs → Internal postbacks, so several answers are on one screen.

1. Is dry-run still on?

This is the most common cause, and it is easy to forget. On Manage → CAPI integrations, open Meta. The switch Dry-run (build + log the payload, send nothing) is on by default — a fresh setup never sends anything until you turn it off.

With dry-run on, the event is built and audited but no HTTP request leaves the tracker. In Logs → Internal postbacks the outcome is dry_run. Turn the switch off and save.

2. Did the click carry an fbclid?

Meta matches a server-side event back to the ad click using click identifiers, not the tracker's click id. The tracker captures fbclid from the ad URL automatically and stitches it with the _fbc and _fbp cookies — you do not map it.

Check the click: open Logs → Clicks, find a recent click from your Meta campaign, and look at its URL — it should contain fbclid=. A redirect, a landing page or a URL-builder that strips query parameters can drop it. In the conversion record, the derived values are fbc (fb.1.<timestamp>.<fbclid>) and fbp. If both are empty, the click arrived without them.

3. Is the dataset/pixel id and token correct?

On the Meta panel in Manage → CAPI integrations, the id and the token must belong together and to the right dataset:

  • Fallback Dataset / Pixel ID and Fallback access token apply when no pixel record is bound.
  • If you use pixel records, each has a Pixel / Dataset ID and an API key / Access token, and must be bound to a traffic channel or an offer.

A wrong pair fails authentication at Meta and lands in Internal postbacks as outcome failed, with a non-2xx HTTP code and Meta's error text in Response. An id with no bound pixel yields not_configured. Use Send test event to validate credentials directly.

4. Is the conversion's status in the list you send?

The panel has a row of checkboxes, Send these conversion statuses. If the conversion's status is not ticked, the send is skipped silently — the event never reaches Meta and no row appears in Internal postbacks. The defaults are lead, sale and upsale.

Also confirm the status has an event name. The tracker maps statuses to Meta events (for example sale → Purchase). With pixel records, the pixel's Default event name applies unless a Custom conversion matching row overrides it. A status that is sent but maps to no event is skipped before a request is made.

5. Did a duplicate get suppressed?

A send is claimed once per click id + status. If the same conversion is processed again — a repeated postback, a retried delivery — the duplicate is suppressed and nothing is sent. Like the status gate, a suppressed duplicate writes no row to Internal postbacks. That is normal and not a fault: if the first send succeeded, Meta already has the event.

Do not confuse this with inbound de-duplication at /pb, which suppresses a repeated transaction id or an identical anonymous status + payout within about 60 seconds. Both mean “already handled”, not “lost”.

6. Is a test event code set?

If Test event code is filled in on the Meta panel, every event is routed to the Test Events tab of Meta's Events Manager instead of the normal event stream. Events sent with a test code do not appear as conversions in your ad reporting. If you set one while testing, clear it and save — otherwise sends look successful while Meta's main view stays quiet.

7. Read Logs → Internal postbacks

This is the outbound audit and the final word. Open Logs → Internal postbacks and look at the newest rows. The columns are Time, Click id, Platform, Pixel, Event, Status, HTTP, Outcome, Attempts and Response.

OutcomeWhat it meansWhere to look next
sentMeta accepted the event (2xx).Matching, not delivery — check the click's fbc/fbp.
failedMeta refused it; read Response.Usually token, dataset or payload — fix per the error text.
dry_runBuilt and logged, nothing sent.Turn off dry-run.
not_configuredNo usable dataset id or token.Fill the fallback fields or bind a pixel.
not_implementedThe pixel belongs to a platform whose sender is not live.Only Meta sends events today.

Transient failures — a network error, 429 or 5xx — are retried up to three times; Attempts shows how many tries it took. A 4xx is terminal. If you see no row at all, recheck steps 1, 4 and 5 — a skipped send writes none.

Fire a known conversion to compare

To exercise the whole path deliberately, fire a postback for a real click from your Meta campaign. Copy the click id from Logs → Clicks, then:

curl "https://YOUR-TRACKER-DOMAIN/pb?clickid=YOUR-CLICK-ID&payout=25&status=sale"

A 200 with {"status":"ok",…} means the conversion was recorded; the tracker then queues the Meta send in the background. Watch Logs → Internal postbacks a moment later for the outbound result. The CAPI integration page covers each setting in full.

“No row” is not “no attempt”

A send skipped by dry-run, status filtering or duplicate suppression leaves no Internal postbacks row. Before assuming the sender is broken, confirm dry-run is off and the status is ticked — those two account for most silent cases.
