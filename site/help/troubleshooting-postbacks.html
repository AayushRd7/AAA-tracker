Postback not recorded (400 / 403 / no match)

Diagnose a postback that never landed: 400 and 403 responses, click ids that do not match, and where to confirm what arrived.

Updated 5 October 2026

First, confirm what the network sent

Before changing anything, open Logs → S2S postbacks. Every inbound call is listed there, whether it was accepted or rejected, so the log tells you which of the cases below you are actually in. If the call is not there at all, the problem is on the network's side or in the URL you gave it — not in your parameter mapping.

400 — invalid status or payout

A 400 means the tracker understood the call but refused the values. There are just two common causes:

  • Unknown status. The status the network sent is not one of lead, sale, upsale, rejected, hold, trash, and is not a custom status you have defined. Check the spelling the network uses and either map it in the network's postback template or define the status in Settings.
  • Non-numeric payout. The payout value contains a currency symbol, a comma decimal separator, or text. Send a plain number — the currency is not part of the payout and is not accepted on this endpoint.

Remember the aliases: if the network sends type instead of status, or sum instead of payout, that is fine and does not cause a 400. An empty status defaults to lead, and an empty payout to 0 — those are not errors either.

403 — postback security

A 403 means the call was blocked before it was read. Two controls can block it, both under Settings → Postback security:

  • Secret key. You have required a key, and the network did not send it. The key can travel as ?key=, ?secret=, or the X-Postback-Key header. Add it to the postback URL you gave the network, or remove the requirement.
  • IP allowlist. You have restricted callers to a list of IPs or CIDR ranges, and the network's server is not on it. Networks frequently send from a range that changes; if you cannot pin it down, either widen the allowlist or turn the IP check off and rely on the secret key instead.

If a mirror or a proxy sits between the network and the tracker, the address the tracker sees may be the proxy's, not the network's.

200 but no conversion appears

If the log shows a 200 and the response was {"status":"ok",…}, the conversion was recorded. If you cannot see it, you are usually looking at the wrong click.

The click id does not match

The most common cause is that the click id never made it round the loop. The tracker appends click_id=… to the offer URL automatically, but almost every network reads its own parameter. If you did not add that parameter to the offer's Target URL — for example &sub1={click_id} — the network has nothing to send back, and the postback arrives with an empty or wrong click id.

To confirm: open Logs → Clicks, copy a recent click id, and post it by hand. A {"status":"ok",…} answers whether the endpoint works; then compare that click id with the one your network is actually sending.

It matched, but not the click you expected

When the click id cannot be matched, the tracker falls back to the transaction id, then to unique sub-ids within its window, then records an unattributed row. If your network sends an old or reused transaction id, the fallback can attach the conversion somewhere unexpected. Check the conversion in Reports → Conversions and delete or correct it from there.

Nothing arrived at all

  • Wrong URL shape. The endpoint is https://YOUR-TRACKER-DOMAIN/pb. If you pasted the legacy path form, it redirects, but a network that does not follow redirects will see nothing.
  • Wrong domain. The postback URL must point at the same tracker domain your campaign link uses. A staging or old domain will accept the call into a place you are not looking.
  • The network only fires on certain statuses. Many networks send a postback for approved sales only. A pending or rejected conversion may simply never be reported.
  • The network is quiet. Health centre shows the last successful postback per source; if it stopped at a specific time, the problem is on the network side.

A checklist

  1. Open Logs → S2S postbacks and find the call.
  2. If 400 — fix the status name or send a plain numeric payout.
  3. If 403 — fix the key in the URL, or the IP allowlist.
  4. If 200 — open Logs → Clicks, fire a known click id by hand, and compare.
  5. Confirm the offer's Target URL carries the network's own click-id parameter (for example &sub1={click_id}).
  6. Confirm the postback URL points at your live tracker domain and uses the /pb?… query form.

The manual test

There is no test-postback button. Fire a click on the campaign link, copy the click id from Logs → Clicks, then call /pb with curl. That exercises the same path a network uses and rules the endpoint in or out immediately.
