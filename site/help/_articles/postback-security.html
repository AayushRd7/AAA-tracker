Why an open postback URL can be abused

Your inbound postback endpoint, https://YOUR-TRACKER-DOMAIN/pb, has to be reachable by every affiliate network you work with. That also means it is reachable by anyone else who learns the URL. An attacker who knows a valid click id — or who can guess one — can post a fabricated conversion and quietly change your numbers:

  • Padding revenue. Fake sale postbacks inflate payout and revenue, which flatters ROI, EPC and every report that reads them.
  • Hiding bad traffic. A stream of fake lead conversions can mask a source that is really underperforming.
  • Polluting attribution. Junk conversions tie themselves to real clicks and distort which campaign, offer or creative looks profitable.

The endpoint is public by design, so the fix is not to hide it but to require proof that a caller is allowed to use it.

The two controls

Both live in Settings → Postback security. Turn the panel on with the switch Require a secret key or IP allowlist for inbound postbacks, then fill either or both fields. When the panel is enabled, a postback must satisfy every non-empty check. If you enable it and leave both fields empty, postbacks are still allowed — so set at least one.

ControlFieldWhat it enforces
Secret keySecret keyEvery postback must carry a matching key, or it is refused.
IP allowlistAllowed IPsOnly callers whose source IP is listed may post. Accepts a comma-separated list of IPs and CIDR ranges, for example 203.0.113.5, 10.0.0.0/8.

Use the key alone when a network posts from a range that changes; add the allowlist when the network can give you a stable set of sending addresses.

How the key travels

The key is accepted in three places, so you can fit whichever shape a network's postback template supports:

  • a ?key= query parameter,
  • a ?secret= query parameter,
  • an X-Postback-Key request header.

For a URL-shaped template, append the key to the postback URL you hand the network:

https://YOUR-TRACKER-DOMAIN/pb?clickid={clickid}&payout={payout}&status={status}&key=YOUR-SECRET

If the network allows custom headers instead, keep the URL clean and pass the same value as X-Postback-Key. Either form works; do not put the key in both.

The exact 403 a blocked postback gets

A postback that fails either check is refused before it is read. It gets HTTP 403 with a JSON body naming the reason:

{"detail":"Invalid or missing postback key"}

An IP failure reads instead:

{"detail":"Client IP '203.0.113.9' is not in the allowlist"}

The attempt is also written to Logs → S2S postbacks with the result blocked and the same reason, so you can see which control refused it. Note that the check happens after the click id and payout are parsed but before any conversion is recorded — a blocked postback never becomes a conversion.

Test it with curl

Use a real click id from Logs → Clicks, then call the endpoint with and without the key:

# with the key — accepted
curl "https://YOUR-TRACKER-DOMAIN/pb?clickid=YOUR-CLICK-ID&payout=25&status=sale&key=YOUR-SECRET"

# without the key — 403
curl -i "https://YOUR-TRACKER-DOMAIN/pb?clickid=YOUR-CLICK-ID&payout=25&status=sale"

Or send the header instead of the query parameter:

curl -H "X-Postback-Key: YOUR-SECRET" "https://YOUR-TRACKER-DOMAIN/pb?clickid=YOUR-CLICK-ID&payout=25&status=sale"

A correct call answers 200 with {"status":"ok",…}. A blocked one answers 403 as above. Testing an IP allowlist from your own machine is less direct: your address must be the one the tracker sees, which may be a proxy in front of the network.

Enable it before you hand the URL over

Turn on the key before you paste the postback URL into a network's settings. The key then travels inside the URL the network stores, so there is nothing to re-edit later. Adding a key after a network is already live means every postback fails with a 403 until you update that network's template too.

Keep the key, watch the logs

Treat the secret like any credential: give a different value per workspace, rotate it if it leaks, and update the networks in the same sitting. After any change, watch Logs → S2S postbacks for a blocked result — it is the fastest signal that a network is still sending the old value.
