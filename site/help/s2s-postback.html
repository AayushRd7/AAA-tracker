Server-to-server postbacks: the complete reference

The inbound postback URL, every accepted parameter alias, default statuses, de-duplication and the exact responses you get back.

Updated 5 October 2026

The inbound URL

A server-to-server (S2S) postback is how your affiliate network tells the tracker that a conversion happened. The network calls a URL on your tracker domain; the tracker records the conversion against the click and answers. The endpoint is:

https://YOUR-TRACKER-DOMAIN/pb?clickid={clickid}&payout={payout}&status={status}&tid={tid}

The four parameters above are the ones a network's postback template usually fills. Only the click id is really the point of the call — see the defaults below for what happens when the rest are empty. The endpoint accepts GET, POST and HEAD. If a network is configured with the older path form of the URL, that form redirects to this query form, so existing templates keep working.

Give each network the URL in the shape it expects to fill. If your tracker is on your own domain, copy the postback URL straight out of the network's conversion-tracking settings after you have saved it.

Accepted parameters and aliases

Parameter names are matched case-insensitively and the first non-empty value wins. That means a network that calls the status type and another that calls it event can both post to the same URL without changes.

MeaningAccepted names (first non-empty wins)
Click idclick_id, clickid, click, subid, sub_id, cid
Statusstatus, type, event, conversion_type
Payoutpayout, sum, amount, revenue, price
Transactiontid, transaction_id, external_id, txn, transactionid

The tracker also accepts pass-through values sub_id_1 through sub_id_10, external_id and transaction_id — they are stored on the conversion for reporting and for attribution fallbacks.

Defaults when a field is missing

  • A missing status is recorded as lead.
  • A missing payout is recorded as 0.
  • There is no currency parameter on /pb. The currency a conversion is recorded in comes from the offer or the workspace, not from the postback.

Built-in statuses are lead, sale, upsale, rejected, hold and trash. Custom statuses can be defined in Settings, and an unknown status is rejected rather than stored.

What happens to revenue and status

Repeat postbacks for the same click accumulate payout and revenue — this is how lifetime value builds up over several conversions — while the recorded status reflects the latest call. So a click that first reports lead and later reports sale ends up as a sale, with both amounts added together.

Duplicates are guarded. A repeat carrying the same transaction id, or an identical anonymous status + payout inside roughly a 60-second window, only bumps the postback counter; revenue is not added a second time. A duplicate call is still a success from the network's point of view.

Attribution and the clickless path

The ideal postback carries the click id the tracker generated. When it cannot be matched, the tracker falls back in order:

  1. match on the transaction id, then
  2. match on unique sub-ids inside an attribution window, then
  3. record an unattributed row so the conversion is not lost.

An unattributed row still appears in reports and can be re-attributed later from the conversion log. The clickless conversions page covers the import path and the window in more detail.

Responses

ResponseMeaning
200 {"status":"ok",…}The conversion was accepted and recorded.
200 {"status":"rejected",…}A rule blocked the conversion, but the call was understood.
400Invalid status, or a non-numeric payout.
403Postback security denied the call — bad or missing key, or an IP outside the allowlist.

Securing the endpoint

/pb is public by design — any network you work with has to reach it. You can require proof with a secret key, passed as ?key=, ?secret=, or the X-Postback-Key header, and optionally restrict callers to an IP allowlist (comma-separated IPs or CIDR ranges). Both are configured in Settings → Postback security. A call that fails either check gets the 403 above. See Securing your postback URL.

Confirming what arrived

  • Logs → S2S postbacks shows inbound calls as they land, including rejections and their reason.
  • Reports → Conversions is where the recorded conversion can be edited or deleted.
  • Health centre shows the last successful postback per source, which tells you quickly whether a network has gone quiet.

If nothing lands

Work through Postback not recorded: it splits the problem into the 400 and 403 cases and the case where the click id simply does not match.
